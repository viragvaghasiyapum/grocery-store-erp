# Performance and scalability audit

**Audited:** 9–11 October 2026

**Scope:** Current application code and schema, `implementation.md` §17, the existing audit, data generator, benchmark, and UI call sites.
**Result:** **Not ready for the requested scale.** A corrected five-year synthetic store with 7.83 million sale-line and movement rows combined, and more than eight million records including bills, was generated and exercised. Several interactive paths exceeded their targets by orders of magnitude; an isolated 10% store also made the desktop UI unresponsive during rapid navigation through Money out. Normal sale transactions remained atomic in the exercised service paths.

This file is the single source of truth for this audit. Priority means release risk, not proof of a measured slowdown. `Confirmed` means the code or SQL has the stated behavior; `needs measurement` means its cost or failure threshold has not been established on the target hardware.

## Scale and evidence boundary

`implementation.md` §17 specifies 20,000 products, about 150,000 lots, 640,000 bills, and 3.8 million bill lines over five years, with about one-gigabyte database and subsecond interactive targets. The generated data also creates roughly one stock movement per bill line, so the combined row count exceeds 50 lakh (five million) even at the documented default scale. That alone is **not** evidence that a *single* five-million-row table, or a further five-million-row growth increment, is fast. The 1.35× fixture measured below supplies at least five million `sale_line` rows and five million `stock_movement` rows, plus proportionate related data.

The recorded 20,000-product import/search result in `implementation.md` (4.890 s import, 0.491 ms p95 search) uses `tools/GroceryErp.Benchmarks/Program.cs`, which creates products but no lots, bills, or stock movements. It therefore did not exercise the queries that failed below. I repaired `tools/GroceryErp.DataGen/Program.cs` after its original 10% run exhausted hot-product stock. A first complete run then exposed **2,130,496 sale lines assigned to already expired lots** despite passing integrity/FK/cache checks. The generator now enforces sale-date expiry, verifies this invariant before publishing, and builds a three-level category tree. A second complete run with fixed seed 27092026 passed those checks. Its sales are direct synthetic SQL inserts with randomized dates and no FEFO allocation; real service sales, returns, damages, vendor payments, and vendor returns were exercised separately on disposable copies. The generator still gives each purchase roughly 5–6 lines rather than the plan's 2–40-line spread, and it does not simulate realistic multiple-terminal traffic. The `docs/perf` directory contains only a recording guide; measured results and conclusions for this task live here. SDK 10.0.401 was already present in the ignored `.tools/dotnet` directory; `global.json` now includes a portable `sdk.paths` entry and `dotnet --version` resolves 10.0.401.

**SDK and test validation:** The final `dotnet build GroceryErp.slnx -c Release --no-restore` passed with zero warnings/errors. Project-level tests passed: Core 10/10, Architecture 1/1, Integration 91/91, UI 4 passed/2 opt-in journeys skipped. The opt-in scale UI journey was then run separately and failed on the reproduced Money out stall. A UI report-pagination smoke test timed out when all test projects ran concurrently, then passed when the UI project was rerun alone; this timing sensitivity should be isolated. The first post-migration integration run found three hardcoded schema-version-10 assertions; they now use `MigrationRunner.LatestVersion`, and the rerun passed. An earlier pre-migration integration run failed once in `PrintJobJournalTests.InterruptedJobs_RemainForReview_AndRetryKeepsOriginalSnapshot` with an SQLite `ObjectDisposedException`; subsequent runs passed, so this intermittent failure remains worth isolating. `dotnet test GroceryErp.slnx` previously reported zero tests and exit code 5, while project-level commands discovered tests; use the latter until solution-level discovery is fixed. These are functional checks, not scalability evidence.

## Measured scale run — 9–10 October 2026

The corrected generator completed seed **27092026** at its default five-year scale. The database contained **20,000 products, 150,000 lots, 26,000 purchases, 640,000 bills, 3,840,445 sale lines, and 3,990,445 stock movements**. Its file was **1,460,269,056 bytes (1.36 GiB)**. Generation checked SQLite integrity, foreign keys, the stock-cache reconciliation view, and zero sales after lot expiry before publishing; a follow-up data-shape query found zero expired sale lines and 30 third-level categories. Synthetic sale inserts bypass the service and the dataset initially has no returns, voids, or audit rows; the service exercises below add several document types to a separate copy. This is over five million records in total, but neither main fact table reaches five million by itself.

Environment: 13th Gen Intel Core i7-13700HX, 16 cores/24 logical processors, 16.9 GB physical RAM, NTFS D: volume, .NET SDK 10.0.401, Release build, local SQLite file. `tools/GroceryErp.ScaleAudit` measures real application services in a console process with a fixed business date of 26 September 2026. Each operation below is a **single timed call**, mostly sequential. The unindexed/indexed paired trial used copies of the first, expiry-invalid fixture; the corrected run has the index from migration 011. Run times include cold-cache/thermal variation, so the paired trial isolates the large index effect while the corrected run is the acceptance baseline. These are **not p95, UI-ready, or simultaneous cashier-load measurements**. The paired trial added only `CREATE INDEX product_lot(product_id)` followed by `ANALYZE product_lot`; its main database grew by 1,622,016 bytes before service writes.

The tested index is now application migration **011**, named `ix_product_lot_product`. A version-10 full-store copy upgraded to version 11 in 492 ms in the audit harness (which deliberately used `NullMigrationBackup` on its disposable copy); the migrated copy's broad catalog query took 399 ms and its low-stock query 85 ms. The actual application migration path creates a pre-migration backup for an existing store, so its first-launch elapsed time includes backup cost. The isolated index trial grew the main database by 1,622,016 bytes; 20 warm sale commits showed no visible regression in this small sample, but write amplification under sustained load remains unmeasured.

## Findings and required changes

### P0 — release blockers for the stated scale

| ID | Finding and evidence | Consequence at scale | Required change and verification |
|---|---|---|---|
| P0.1 | **Product search still returns up to 20,000 rows.** `CatalogService.SearchAsync` computes `SUM(qty_on_hand)` in a correlated subquery in the select list and again for the low-stock filter, plus a correlated FEFO lookup. `ProductsPage.RefreshAsync` requests `Limit: 20_000`. Migration 011 now supplies the general `product_lot(product_id)` access path; the full broad request improved from 90.47 s to 0.399–1.079 s across indexed runs, still far above the query/UI target. **Measured.** | Large searches allocate and bind thousands of rows; even after the index, the desktop cannot meet its search-to-visible target. | Page the product list with stable `(name COLLATE NOCASE,id)` ordering; compute stock/FEFO only for a small visible page. Keep low-stock filtering correct through a maintained aggregate or a measured query plan. Benchmark empty, short, FTS, category, and low-stock searches under UI load. |
| P0.2 | **Inventory and other lists materialize whole result sets.** `InventoryService.GetLotsAsync`, `GetOverviewAsync`, `GetLedgerAsync`, `GetStockCountAsync`; `MoneyOutService.GetExpiryAsync`; `PurchasingService.GetVendorLedgerAsync`/`GetVendorLotsAsync` have no page limit. `ProductStockWindow` requests ledger from `DateOnly.MinValue` through `DateOnly.MaxValue`; `StockPage` defaults to 2000–2100. Ledger calculates a running window balance before filtering by date. `MoneyOutPage.RefreshAsync` binds three expiry lists and loads all lots into a picker; `LabelBatchWindow` also loads all lots to filter selected IDs, and `PurchaseEntryWindow` preloads 5,000 products. **Confirmed; corrected 10% UI run timed out after Money out at about 1.66 GB working set; the first fixture reached about 2.06 GB.** | A popular product's history, growing lot table, or large stock count can occupy large memory and freeze the UI. | Add bounded keyset pages with stable `(date,id)` or `id` cursors and server-side filters. For ledger balances, obtain an opening balance before the page/range, then calculate only visible rows. Query lot IDs directly for pickers; never load all lots merely to select one. Keep a small visible page in UI state. Repeat the UI test after bounding results. |
| P0.3 | **Restore has no database-wide quiesce barrier.** `BackupService.ApplyRestoreCore` locks backup calls, takes a pre-restore backup, checkpoints, calls `SqliteConnection.ClearAllPools()`, and renames the live database set. `DbExecutor.ReadAsync` and `WriteAsync` can still start or hold connections. **Reproduced:** an active reader caused `BackupInvalid` after 10.92 s on a 10% copy; no pending marker or corruption was found afterward. | An in-progress restore can fail with a busy database; overlap with new work during file replacement remains a code-supported race. | Gate all database entry points and direct maintenance/backup connections; stop new work, await active work, close pools, then checkpoint and swap. Keep the barrier through shutdown/restart. Test queued writes, printing/refreshes, and process interruption. Preserve recovery marker and rollback behavior. |
| P0.4 | **Startup scans the entire movement ledger.** `MaintenanceService.CheckBeforeShellAsync` queries `v_lot_cache_mismatch LIMIT 1`; that view groups *all* `stock_movement` rows by lot before comparing cached stock. The corrected full-store service check took 52.17 s and the 5.38m-movement fixture took 24.51 s, both against a `<2 s` target. **Measured path; cache/state variation needs isolation.** | Login time grows with history. If a mismatch exists, `RebuildStockCacheAsync` runs a full correlated rebuild in one write transaction. | Move full reconciliation to scheduled/offline integrity work. At startup use a durable clean-shutdown/recovery signal plus bounded checks, and keep a way to request full validation. Measure cold and post-crash starts at 5m+ movements; rebuild in controlled maintenance mode with progress and recovery. |
| P0.5 | **Unbounded sales-history export builds the entire result in memory and then a ClosedXML workbook.** `SalesHistoryPage.Export_OnClick` pages the database but appends every row to `all`, constructs a `TabularReport`, and `ReportOutputService.ExportExcel` constructs all worksheet cells. ### P2 — hardening and instrumentation

* Instrument query time, returned row count, read concurrency, writer-gate wait, transaction duration, WAL bytes, backup/checkpoint time, and UI refresh age. Record slow-query parameters without customer data.
* Add a bounded retry/backoff policy for `SQLITE_BUSY` caused by external/process-level contention; avoid replaying an ambiguous committed write without an operation ID. The current 5 s busy timeout is not a substitute for work scheduling.

* Define behavior for a full disk, corrupted WAL, process kill during commit, and failed print after a committed sale. Verify recovery and operator messaging; do not label all such failures “race conditions.”

## Concurrency and crash assessment

**Existing defenses:** `DbExecutor.WriteAsync` serializes writes and uses an immediate SQLite transaction; stock movement triggers update and validate cached lot stock; sale completion, void, returns, purchases, and several money-out operations use operation IDs; normal launches use a single-instance mutex. These substantially reduce overselling and duplicate sale completion in the normal single-process path. Backups have an instance lock, a unique working directory, checksum verification, and a partial-to-final rename. Reports already have a refresh-version guard. These facts supersede the older audit's claims that backup creation lacks serialization/final verification and that report refreshes generally overwrite newer results.

**Remaining races:** Restore can overlap database work (P0.3); scanner and history navigation can reorder UI state (P1.6–P1.7). Lot price/active updates in `InventoryService` are ordinary serialized writes without operation IDs or a revision check; repeated clicks are generally idempotent for the same value, but concurrent *different* edits are last-write-wins. Choose an explicit revision/compare-and-swap rule if staff can make competing edits. The in-process gate does not coordinate an external SQLite writer; the database constraints and busy handling remain the last defense.

**Crash/hang exposure:** The strongest code-supported risk is memory exhaustion or apparent UI hang from unbounded result/export materialization, plus shutdown/startup delays and failed restore under active connections. The audit found no basis to claim that a normal sale transaction will partially commit. A specific crash probability cannot be estimated without the full-scale and fault-injection runs.
