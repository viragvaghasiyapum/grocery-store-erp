# Phase-wise performance and scalability plan

**Plan updated:** 11 October 2026

**Project phase reference:** `implementation.md` §21.1 (project phases 0–7).

**Audit baseline:** `optimization.md`, audited 9–11 October 2026. The complete current audit is reproduced verbatim in the appendix so that its measurements, qualifications, priorities, and required changes remain exact. Keep `optimization.md` as the current source of truth for audit measurements.

This is a plan, not a claim that the application has passed its scale targets. The corrected baseline fixture has 3,840,445 `sale_line` and 3,990,445 `stock_movement` rows. The generated 1.35× fixture has **5,179,009 sale lines and 5,381,509 stock movements**, and its first service pass still found slow paths. Successful service calls do not establish UI latency, p95 latency, sustained concurrency, or crash recovery. Migration 011's `product_lot(product_id)` index and the corrected generator are already implemented; preserve them and measure any further change against that indexed baseline.

## Additional code findings outside the recorded audit

These findings began as confirmed code paths. Follow-up service and render measurements now cover part of each path; the status table below separates measured behavior from the remaining acceptance work. Their failure threshold on the target store PC remains open.

| ID | New finding and evidence | Change and verification |
|---|---|---|
| N1 | **Shell expiry badge loads every alert row.** `ShellWindow`'s `Loaded` handler calls unbounded `MoneyOutService.GetExpiryAsync()` and counts buckets in memory before updating the badge and possibly showing a modal popup (`ShellWindow.xaml.cs`, `MoneyOutService.cs`). This shares the broad expiry view cost identified in P1.9, but also affects the first shell interaction before the Money out page is opened. | Add a count-only service query for the badge and fetch a small alert page only when requested. Keep day rollover and category alert rules correct. Measure shell time to usable navigation with many expiry lots and popup enabled/disabled. |
| N2 | **Held/draft picker and asset register have no page bound.** `SalesService.GetHeldAsync` and `GetDraftsAsync` return all matching bills and `BillingPage` concatenates them; `AssetService.GetAssetsAsync` returns the whole register with two correlated depreciation lookups per asset and `AssetsPage` binds it all. A long-lived store could accumulate many drafts and disposed assets. | Add search/filter and stable bounded pages, with direct ID lookup for resume/edit. Measure broad and selective picker loads, asset list plans, memory, and UI latency with aged drafts and many historical assets. |
| N3 | **Purchase history has a silent fixed ceiling.** `PurchasingService.GetPurchasesAsync` defaults to the newest 500 (maximum 5,000), and `PurchasesPage.RefreshAsync` shows that one result with no older-page navigation. The data generator has about 26,000 purchases. | Add cursor navigation and date/vendor filters; retain a small default page and expose older purchases. Verify users can reach first, middle, and oldest documents and that order remains stable during new postings. This is a completeness and scale usability issue; it is not evidence of a slow current query. |
| N4 | **Print work can delay receipts behind large label jobs.** `ReceiptPrinter` uses one bounded 128-job channel and one worker for labels, receipts, day-end, and drawer. A whole label batch is serialized into the print-job journal, rendered into one byte array by `TsplLabelBuilder.BuildBatch`, and sent as one worker action; label copies can be set to 100,000 per selected row. | Bound batch bytes/copies, stream or split label jobs into resumable chunks, and prioritize cashier receipt/drawer work while preserving journal order and reviewed retry semantics. Measure receipt-start `<1 s` with an active label batch, failed/offline printer, and day-end job; record queue age and memory. |
| N5 | **Opening-stock preview holds a database read while parsing the workbook.** `OpeningStockExcelImporter.DryRunAsync` creates `XLWorkbook`, loops every row, and queries the product by SKU inside one `DbExecutor.ReadAsync` callback. The workbook and preview are materialized, and the connection stays open for the parse. `ProductExcelImporter` also materializes the workbook/preview and uses one transaction with repeated per-row lookups and audit writes during import. P1.4 already calls for chunking imports; these are the specific preview and lookup paths to address. | Parse with a bounded workbook/import size and progress/cancellation, preload or batch SKU rules, release the SQLite read promptly, and make large writes restartable/idempotent where safe. Measure preview/commit time, peak memory, WAL growth, reader lifetime, and POS p95 during a 20k-product and large opening-stock import. |
| N6 | **Interactive report export and A4 preview run synchronous whole-output work on the UI thread.** `ReportsPage.Export_OnClick` calls `ReportOutputService.ExportExcel` directly; `Preview_OnClick` calls `CreateA4` directly. The latter measures every cell and builds every `FixedPage` of a `FixedDocument` before showing the viewer. P1.3 covers report query/output size but does not cover this UI execution path. | Run bounded export work off the UI thread with progress, cancellation and temporary-file rename. Use a capped printable result or lazy/paged document rendering; show the cap clearly. Measure UI responsiveness and peak memory with the maximum 50,000-row interactive report, including a multi-band report. Verify numeric cells and printed layout. |
| N7 | **Weekly maintenance can occupy the first shell session.** `MaintenanceService.RunAfterShellAsync` makes a daily backup if due, then runs `PRAGMA integrity_check`, `foreign_key_check`, and FTS integrity verification when the weekly date is due. It runs after the shell, so the full-history checks can overlap cashier work. The original audit measured backup and discussed startup/shutdown maintenance, but did not measure this weekly path under POS load. | Schedule heavy integrity work for an idle/maintenance window, report progress and outcome, and avoid repeated full checks after interruption. Test first launch after seven days, active sale commits, cancellation/restart, and WAL/backup interaction. Maintain a way to run a full check on demand. |
| N8 | **Data-root relocation copies the entire data tree during startup.** `DataRootRelocator.ApplyPending` recursively copies every directory/file from the old root, including retained backups, then hashes the database and WAL and runs database checks before switching the bootstrap. It also discards and recopies a recognized interrupted staging folder. This is a code-supported startup and disk-capacity risk; no full-store relocation timing was recorded. | Measure source-tree size, peak temporary disk, copy/verify/startup time and interrupted retry with several retained backups. Consider a resumable copy or explicit operator maintenance window while preserving validation and rollback safety. |
| N9 | **Customer lookup is capped but can scan the customer table.** `SalesService.SearchCustomersAsync` uses `name LIKE '%query%' OR phone LIKE '%query%'` and `LIMIT 100`; the leading wildcard cannot use an ordinary name/phone B-tree prefix lookup. `CustomerWindow` invokes it for the POS picker. No large customer fixture or picker latency was measured. | Keep the 100-row UI bound; measure empty, exact phone, prefix and contains terms at realistic customer counts. Add a selective normalized phone lookup and an FTS/prefix strategy if plans and timings justify it. Debounce/version the picker and confirm the currently selected customer remains reachable. |
| N10 | **Vendor list recalculates balances while populating pickers.** `PurchasingService.GetVendorsAsync` joins `v_vendor_balance`, whose definition sums posted purchases and payments per vendor. Purchases, purchase entry, payments, assets and other screens load this full vendor list. The dashboard's payable metric was covered in P1.1, but repeated vendor-picker loads were not individually measured. | Measure vendor-list and picker latency with 150 and grown vendor counts plus years of purchases/payments. Use a maintained payable projection or an aggregate that avoids repeated historical sums if measured plans require it; keep balances correct for cancellation, returns and payments. |
| N11 | **Stock count search operates on the fully bound count.** `StockCountWindow.FindCountLineAsync` copies `CountGrid.ItemsSource` into a list and scans it by lot code/name, then possibly resolves a barcode and scans the list again. P0.2 covers full stock-count materialization; this adds the explicit in-count search path that must survive paging. | Provide server-side lot/product/barcode lookup within the count scope and jump to the matching page. Measure search-to-edit latency and memory in a 2,420-lot scoped count and a 150,000-lot whole-store count. |
| N12 | **Two report paths bypass the common row cap.** `ReportService.GetReportAsync` routes Salary Register to `GetSalaryMatrixAsync` and Asset Schedule to `GetAssetScheduleAsync` before the normal `Limit + 1` query. The salary path loads every matching employee-month row and builds a dynamic column for every month in the requested range; the asset path loads all posted periods and projects through the requested end month. Their output size is not limited by `ReportFilter.Limit`. | Apply explicit date-span, row and column bounds suitable for interactive display; page or export large salary matrices and cap/project asset schedules deliberately. Measure multi-year ranges, many employees, old assets, memory and UI/A4/Excel behavior. Verify totals and posted/projected status after capping. |
| N13 | **Draft stock-count picker groups every count line.** `InventoryService.GetDraftCountsAsync` joins `stock_count` to `stock_count_line`, groups all draft lines, then returns every draft. A large abandoned whole-store count can make opening the picker depend on many count-line rows even when only one summary is shown. | Maintain counted/total counters or use measured indexed aggregates and page draft summaries. Test many draft counts, a 150,000-lot draft, and concurrent POS writes; keep summary counts correct after edits, refresh, cancel and post. |
| N14 | **Vendor payment purchase picker exposes only the newest 500 posted purchases.** `PurchasingService.GetVendorPurchaseChoicesAsync` has `LIMIT 500` and no cursor or search parameter. Long-lived vendors may have older unpaid purchases that cannot be chosen in the UI. The bound protects memory but does not preserve historical reachability. | Add invoice/document search and stable paging or a direct purchase-ID lookup. Verify oldest/middle/newest choices for a vendor with more than 500 posted purchases and measure search latency. |

## Work phases and exit gates

### Phase 0 — Baseline, observability, and repeatability

**Project ownership:** Foundations (1) and Hardening (7). **Purpose:** establish trustworthy before/after evidence without treating the existing one-machine calls as acceptance results. Use the search, filter, and query coverage register above as the inventory.

1. Preserve the corrected seed 27092026 baseline, the generated 1.35× fixture and migration 011. Capture exact commit, SDK/SQLite versions, CPU/RAM/SSD, row counts, database/WAL bytes, and cold/warm state. Extend acceptance copies with realistic returns, voids, backdated postings, multiple-terminal activity, and the documented 2–40 purchase-line spread; give loose products PLUs compatible with the scale-rule parser. The generated strong fixture already passed integrity, foreign-key, cache and post-expiry validation; repeat those checks after service writes and fault tests. Record generator limitations when a distribution is synthetic.
2. Add P2 instrumentation for query duration/row count, active readers, writer-gate wait, transaction time, WAL bytes, backup/checkpoint time, print queue age, and UI refresh age without customer data. Capture p50/p95/p99 and `EXPLAIN QUERY PLAN` for each hot query and parameter shape. Use read/write load together, not only sequential isolated calls.
3. Make project-level test commands the baseline until `dotnet test GroceryErp.slnx` discovers tests. Isolate the intermittent print-journal `ObjectDisposedException`, concurrent UI report-pagination timeout, and opt-in Money out navigation stall. Keep the already fixed schema-version assertions. Run the UI project alone when timing-sensitive until the root cause is understood.

**Exit:** reproducible full and stronger fixtures, a measured before-state, working test discovery or a documented project-level gate, and instrumentation that distinguishes DB time, WPF binding/render time, print queue delay, and backup/maintenance time.

### Phase 1 — Bound interactive memory and first response

**Project ownership:** Shell (0), Catalog (2), Stock-in (3), POS (4), Money out (5), Insight (6). **Blocks:** P0.1, P0.2, P0.5; N1, N2, N3, N9, N13–N14; UI portion of P1.3.

1. Page catalog with stable `(name COLLATE NOCASE,id)` cursors and compute stock/FEFO only for the visible page. Preserve correct low-stock filtering through a measured aggregate/query plan. Test empty, short, FTS, category, broad and low-stock searches under UI load.
2. Add stable keyset pages and server-side filters to overview, lots, stock count, stock ledger, vendor ledger/lots, expiry, damage/expense history, and the other broad pickers. Obtain ledger opening balances before the requested range/page. Use direct ID queries for selected lots and small visible UI collections. Include the shell's expiry badge count-only query, held/draft picker, asset register, navigable purchase and vendor purchase-choice history, paged draft-count summaries, and bounded customer search.
3. Separate interactive report caps (roughly 100–500 rows, tuned by measurement) from full exports. Stream Sales History export with bounded memory and progress/cancel/temporary-file rename. Respect XLSX's 1,048,576-row sheet limit by chunking or use CSV. Do not rely on an output `LIMIT` to bound aggregation work.
4. Repeat the corrected 10% rapid-navigation FlaUI journey and then full-scale navigation through every main page and relevant dialog. Measure UI-ready time, peak working set, and visible row count. Include Money out, Products, Stock, Purchases, Assets, Billing, Reports, Sales History and Dashboard.

**Exit:** no unbounded interactive fact/history list, the rapid-navigation Money out stall no longer reproduces, all historical purchase/draft/asset records remain reachable, and full-size export stays within a measured memory budget with validated row counts/types.

### Phase 2 — Make restore exclusive and recovery deterministic

**Project ownership:** Foundations (1) and Hardening (7). **Blocks:** P0.3; restore/crash parts of P2.

1. Gate `DbExecutor` reads/writes and direct database connections, including print-job journal, backup, maintenance, migration and restore connections. Stop new work, await active operations, close pools, checkpoint, then swap; keep the barrier until restart/shutdown. Preserve the verified backup, pending marker and rollback behavior.
2. Exercise active readers, queued writes, print/refresh work, external SQLite contention, low disk, process kill at each restore boundary, and post-restore cold launch. Verify integrity/FKs/stock cache and no lost/duplicate documents. Define recovery/operator messaging for full disk, corrupt WAL, failed print after a committed sale, and ambiguous write outcomes. Add bounded `SQLITE_BUSY` retry only where replay is safe through operation IDs.

**Exit:** restore either completes and validates or recovers the prior store, even with queued work and injected interruption; no new connection enters during the swap.

### Phase 3 — Remove whole-history work from interactive startup and insight

**Project ownership:** Foundations (1), Money out (5), Insight (6), Hardening (7). **Blocks:** P0.4, P1.1, P1.3, P1.8, P1.9; N7, N10, N12.

1. Replace the startup `v_lot_cache_mismatch` full movement regrouping with a durable clean-shutdown/recovery signal plus bounded checks. Keep full stock-cache reconciliation and controlled rebuild in offline maintenance with progress/recovery. Measure normal and post-crash cold start at 5m+ movements.
2. Reduce dashboard repeated stock/expiry/daily-sale work; order/limit top ten in SQL and use coherent snapshots. Page expiry details and compute counters separately or through a maintained projection. Measure vendor-picker balance calculations alongside dashboard payables. Validate day rollover, category alert changes, returns, voids, vendor payments and backdated data.
3. Optimize common month/FY P&L and grouped item/category/GST reports using indexed date ranges and measured summaries where necessary. Rewrite salary month predicates to lexical ranges and bound the Salary Register matrix and Asset Schedule path that bypass the generic limit. Verify business totals with populated reports, not zero-row success. Test 50k export cells, CSV/print output, and visual formatting.
4. Schedule weekly integrity work and backup/retention outside cashier-critical periods. Make close-backup policy explicit after a recent verified backup. Measure low disk, active readers, backup time, extra disk, shutdown, and WAL growth.

**Exit:** cold start `<2 s`, dashboard `<1 s`, month/FY P&L `<200/500 ms`, and background ~1 GB daily backup `<60 s` on target hardware under the documented workload; full integrity remains available and does not monopolize first-use POS.

### Phase 4 — Tune access paths, writes, and UI ordering

**Project ownership:** Foundations (1), Catalog (2), Stock-in (3), POS (4), Money out (5), Insight (6). **Blocks:** P1.2, P1.4, P1.5, P1.6, P1.7; remaining P2 SQL items; N5, N9, N11.

1. Measure candidate indexes and query plans before adding them: `sale(sale_date DESC,id DESC)` with status strategy, `stock_movement(product_id,id)`, `sale_return_line(sale_return_id)`, vendor lot ordering, and `audit_log(at,id)`. Rewrite audit and salary date filters so indexed columns are not wrapped in functions. Run `PRAGMA optimize`/statistics after bulk changes; add `ANALYZE` only if plans need it. Recheck write throughput and file growth at 5m+ rows.
2. Chunk or schedule import and cache repair; limit stock-count rule lookup to supplied lot IDs and scope counts physically. Make lot-code/name/barcode search work within paged counts. Record writer-gate waits, transaction duration, and WAL growth while bills commit. Keep explicit maintenance mode for work that cannot safely chunk. Apply the N5 preview/lookup changes and test imported totals/idempotency.
3. Limit concurrent reads, propagate cancellation/timeouts where SQLite/Dapper supports them, coalesce refreshes, and watch pooled connections and long WAL snapshots. Serialize POS scan/bill-switch actions in arrival order, version bill refreshes, and commit sales-history cursors only after the matching request succeeds. Test burst scans, double Enter, New/Hold/Pay, unknown barcode interruption, and rapid history navigation.
4. Decide and test a revision/compare-and-swap rule for competing lot price/active edits. Keep normal sale atomicity and operation-ID protection; do not infer partial commits from UI reordering.

**Exit:** no normal-operation `SQLITE_BUSY` failures; bounded readers/WAL and POS p95 while imports, counts, dashboard and reports run; no stale bill/history UI state; every adopted index has measured read benefit and acceptable write/storage cost.

### Phase 5 — Printing, output, data move, and release workflow

### P2 — hardening and instrumentation

* Instrument query time, returned row count, read concurrency, writer-gate wait, transaction duration, WAL bytes, backup/checkpoint time, and UI refresh age. Record slow-query parameters without customer data.
* Add a bounded retry/backoff policy for `SQLITE_BUSY` caused by external/process-level contention; avoid replaying an ambiguous committed write without an operation ID. The current 5 s busy timeout is not a substitute for work scheduling.
* Ensure `PRAGMA optimize`/statistics run after bulk load and new indexes; DataGen and migrations already call `PRAGMA optimize`, so verify its effect and add `ANALYZE` only if plans need it.
* Review optional index write amplification and disk growth at 5m+ movement/line rows. SQLite WAL supports concurrent readers and one writer; this architecture can scale a single-store desktop history if reads are bounded and summaries are maintained. It is not a multi-terminal write architecture.
* Define behavior for a full disk, corrupted WAL, process kill during commit, and failed print after a committed sale. Verify recovery and operator messaging; do not label all such failures “race conditions.”

## Concurrency and crash assessment

**Existing defenses:** `DbExecutor.WriteAsync` serializes writes and uses an immediate SQLite transaction; stock movement triggers update and validate cached lot stock; sale completion, void, returns, purchases, and several money-out operations use operation IDs; normal launches use a single-instance mutex. These substantially reduce overselling and duplicate sale completion in the normal single-process path. Backups have an instance lock, a unique working directory, checksum verification, and a partial-to-final rename. Reports already have a refresh-version guard. These facts supersede the older audit's claims that backup creation lacks serialization/final verification and that report refreshes generally overwrite newer results.

**Remaining races:** Restore can overlap database work (P0.3); scanner and history navigation can reorder UI state (P1.6–P1.7). Lot price/active updates in `InventoryService` are ordinary serialized writes without operation IDs or a revision check; repeated clicks are generally idempotent for the same value, but concurrent *different* edits are last-write-wins. Choose an explicit revision/compare-and-swap rule if staff can make competing edits. The in-process gate does not coordinate an external SQLite writer; the database constraints and busy handling remain the last defense.

**Crash/hang exposure:** The strongest code-supported risk is memory exhaustion or apparent UI hang from unbounded result/export materialization, plus shutdown/startup delays and failed restore under active connections. The audit found no basis to claim that a normal sale transaction will partially commit. A specific crash probability cannot be estimated without the full-scale and fault-injection runs.

1. **Bound reads and exports:** page catalog, inventory, ledgers, expiry, vendor views, stock counts, and interactive reports; stream exports. Add stable cursors, direct-ID lot lookups, and UI request versions/scan queue.

3. **Remove full-history work from the interactive path:** replace startup ledger regrouping; optimize dashboard and common period reports with measured summaries; keep full integrity checks offline.
