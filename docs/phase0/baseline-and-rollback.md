## Migration resource budget

Before a future live migration, require free space for the original DB, a verified compressed backup, a rebuilt compact DB, WAL/temporary files and a safety margin. For this 2.43 GB scale, reserve **at least 8 GB additional free disk** after existing files; measure actual peak from a rehearsal and raise the threshold if needed. The observed legacy 25→28 pass took 40.6 seconds, and verified backup took 107.5 seconds. The target migration time is **unmeasured** until its schema and backfill exist; no production time promise is justified. Record table/index bytes with `dbstat`, migration stages, peak disk/WAL, backup/restore time, working set and source parity on the disposable full-size copy before scheduling a shop upgrade.

Candidate budgets from the revised plan: scan to bill line <50 ms p95, product search to visible callback <100 ms p95, bill commit <100 ms p95, eight-result SQL search <30 ms p95, sustained WAL <64 MiB, full-history CSV <512 MiB peak and process working set no higher than the paired baseline without a measured reason. A 350 MiB full-size WPF peak is a candidate on the reference PC. Shop-PC sign-off sets the final gates.

## Rollback procedure for a future schema-29+ cutover

1. Stop the app and confirm there is no active writer. Inspect schema version, lot/stock projection arithmetic, source counts and open/closed annual totals. Verify the backup archive checksum and manifest; retain it outside the database directory.
2. Check free space using the measured rehearsal peak plus margin. If short, stop before any live mutation. Copy the store into an isolated rehearsal root, run migration there, and verify old receipts, invoices, source/lot arithmetic, annual snapshots, foreign keys and integrity.
3. Install the upgraded binary with a schema guard. Old schema-28 binaries must refuse `user_version > 28`; never open the upgraded file with an old binary. Migration scripts start at 029 and run only on the upgraded app.
4. On failure, close the new app, preserve the failed database and logs for diagnosis, then use the existing verified restore staging and exclusive database-swap barrier to restore the pre-upgrade backup. Check checksum, schema, counts, integrity, lot cache, receipts and a cold launch before resuming sales. Do not copy only the main DB over an active WAL store.
5. If compaction or later validation fails after a successful upgrade, stop writes and restore that same pre-upgrade backup with the matching old binary. Replay only independently documented business actions made after the backup; do not silently merge the two databases or reuse operation IDs.

## Adversarial fixture manifest for migration rehearsals

The disposable rehearsal must contain many lots for one hot product; identical batch/expiry from distinct purchase lines; a partly returned purchase; a completed and then returned sale; a refunded sale; expired and blocked lots; zero lots attached to historical rows; direct-origin and internal-use lines; deleted product followed by return; and corrections on 7/8 January and 7/8 April. Current schema 28 cannot encode direct-origin, internal-use and independent annual locks, so those cases become executable as the relevant schema/service phases land. Keep source row IDs, expected fixed-point arithmetic and expected old receipt bytes in the fixture manifest. Tests must cover positive and negative paths, not only empty result timing.

## Baseline test disposition

The initial `dotnet test GroceryErp.slnx -c Release --no-restore` run had 171 passed, 2 intentional opt-in UI skips and 1 failure. `InterruptedPnlBackfill_RebuildsOnNextMigrationRun` had set a fully migrated schema-28 fixture's `user_version` to 15, an impossible interrupted-v16 state; migration 28 then correctly rejected a duplicate column. The test now creates a real schema-15 store, applies the interrupted schema-16 script and reruns the migrator. A new test confirms that the schema-28 binary refuses schema 29 before migration. The full solution run passed **173**, failed **0**, skipped **2** opt-in packaged/scale UI tests; the separate scale journey passed **1/1** after updating a stale Assets locator. Full-size verification evidence is `revision-phase0-valid-verify.json`.

`dotnet format --verify-no-changes` reports a large repository-wide pre-existing formatting drift (including untouched `App.xaml.cs` and report/data files). The same check scoped to the two changed C# test files passes. It was not applied wholesale during Phase 0 because that would create unrelated changes and obscure the baseline. `git diff --check` passes for the changed files.
