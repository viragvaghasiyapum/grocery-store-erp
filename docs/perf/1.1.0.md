# Release 1.1.0 performance evidence — 25 October 2026

This is the revised Phase 9 same-machine pass: the Phase 8 build (commit 66839e3, schema 36) against
release 1.1.0 (schema 37). It is local evidence on the development PC, not the target-shop-PC
acceptance that §3 of the [revised plan](../../revised-implementation-plan.md) still requires.

- PC: VARK, 24 logical processors, .NET 10.0.12, SQLite 3.53.3. The OS file cache was never flushed.
- Store: the preserved schema-36 fixture (47,010 products, 223,272 lots, 27,000 barcodes, 35,100
  purchases, 871,876 sales, 5,193,017 sale lines; 1,807,351,808 bytes), DataGen full scale with the
  Phase 0–8 adversarial additions. Most of its lots are expired with stock still on hand (164,295 of
  223,272), which makes every expiry-dependent read harder than in a shop that writes expiry off.
- Method: `ScaleAudit phase9-profile` on a fresh copy for every run. Each operation runs once under
  the SQL trace (every statement is planned and re-run for rows visited), then 10–30 times alone,
  then mixed: 300 cashier bills with voids and returns, four readers, purchase posts, damage, counts,
  vendor returns and one verified backup at once. The two builds alternated, twice base-first and
  once new-first, plus two further 1.1.0 runs. Ranges below are across runs; run-to-run machine state
  moved every figure by up to four times, so only differences that hold within each pair count.
- Evidence: `artifacts/data/revision-phase9-rehearsal` (`profile-ab/` holds every run and
  `compare.mjs`; `full-size/` the verification, exports, crash, backup, restore and category-batch
  results; `scripts/` the measurement scripts).

Every search shape stays under the 30 ms search gate at p95 (13.1 ms at most). The write paths
executed identical statements with identical plans in both builds; their spread follows run order
(each build was faster in the round it ran second) rather than the build. Only three statement plans
differ, and those use the new `ix_product_barcode_lot` index.

**Current unsold stock** is 6–12 times faster. Both stock aggregates read most lots, so they now
scan the table in order instead of walking `ix_product_lot_product` and `ix_lot_expiry` with a row
lookup per lot.

**Busiest product's reconciliation** (500 lots, 18,262 sale lines) stays at about 0.2–0.65 s. Each
sale line costs a `sale_line` row and a `sale` lookup. A covering `sale_line(lot_id,sale_id,qty)`
index would remove one of the two for about 55 MB of store and backup size; for an on-demand
single-product report and reviewed counts that is not worth it, so it was not added.

**Dashboard** is dominated by counting expired lots with stock from the covering partial expiry
index. The cost is proportional to that count, which is 164,295 in this fixture and small in a shop
that writes expiry off. No change was made.

## Bulk category change

A product's sale lines from before schema 31 carry no category of their own, so changing its
category moves all of them in the category/GST report days inside the batch transaction. On this
store every one of the 5.19 million lines is such a line. A product with 594 lines took 36 ms. A
50-product batch took 1.6–3.0 s for ordinary products and 7.6–8.3 s for the 50 busiest, all of it
holding the single writer. 1.1.0 cuts category batches at 2,000 sale lines (at most 50 products).
Replayed on the full store, 500 ordinary products ran in 60 batches with p50/p95/max 120/138/156 ms,
and the 200 busiest products ran one per batch with 81/172/634 ms (`full-size/category-batch.json`,
`category-weighted.json`). The Excel import still updates up to 100 products per transaction; it
moves report days only for a product whose category the file actually changes.

## Full-history exports

| Report, all dates | Rows | Time | Process peak | Note |
|---|---:|---:|---:|---|
| Sales register | 872,312 | 9.6 s | 87 MiB | streamed page by page; cancel stopped in 4 ms |
| Item sales, before | 27,009 | 19.8 s | 1,027 MiB | every sale line indexed and sorted in memory |
| Item sales, 1.1.0 | 27,009 | 10.6 s | 98 MiB | grouped by product first; large sorts spill to disk |
| Category sales | 81 | 0.1 s | 78 MiB | from the daily projection |

Item sales joined product and category before grouping, so SQLite materialized and indexed all 5.19
million movements and sorted them in memory. 1.1.0 groups by product first and runs every tabular
report and CSV export with `temp_store=FILE` for that connection only. The query alone took 18.7 s
and 1,005 MiB as it was; grouped first it took 12.1 s and 491 MiB with in-memory sorts and 10.0 s and
95 MiB with file sorts. File sorts on the old query took 73 s, and a 64 MiB sort cache took 72 s at
472 MiB, so neither was kept.

## Storage, backup and recovery

- Migration 37 adds the partial `ix_product_barcode_lot` index (one page here, as no barcode names a
  lot). Deleting 50 zero lots in one transaction fell from 73–79 ms to 2.4–4.9 ms.
- Upgrade 36 → 37 on the full store: 23–73 ms across five copies (`profile-ab/migrate-*.json`) at a
  64 MiB peak, plus the verified pre-upgrade backup the app takes first.
- Verified backup of the 1.8 GB store with no other load: 20.4 s at a 76 MiB peak.
- Restore of that backup into an empty data root: 18.8 s; all ten store checks passed afterwards.
- A process killed after its lot update but before commit left zero sale rows, foreign-key
  violations or source mismatches, and `quick_check` was ok.
- After all profiling writes, the crash and the backup, the ten checks passed: report-day, last-sale,
  hourly and dashboard projections, integrity (47 s), foreign keys, every lot against its source
  documents (41.5 s at 74 MiB), sale lines after lot expiry, and interrupted writes.

## WPF

`ScaleUiTests` drove each self-contained published build on its own copy of the store at the PC's
own window size: sign-in, three rounds of every page (30 navigations, with the UI Automation peers
released before each sample), then a Sales History export of all 871,876 bills through the Save As
dialog (`GROCERY_SCALE_UI_ROUNDS=3`, `GROCERY_SCALE_UI_EXPORT=1`). Results are under
`artifacts/data/revision-phase9-ui`.

| Measure | Phase 8 build (GPU drawing) | 1.1.0 |
|---|---|---|
| Working set over 30 navigations | 502 MiB rising to 580 MiB | 285 MiB, then 230–259 MiB |
| Process peak during navigation | 581 MiB | 296 MiB |
| Private bytes, highest sample | 465 MiB | 196 MiB |
| Rows per table page | 15–18 | 17–21 |
| Page control found, after the first | 140–246 ms | 151–316 ms |
| Sales History export, 871,876 bills | 27.9 s, peak 663 MiB | 24.9 s, peak 310 MiB |
| Sign-in window / shell after sign-in | 3.7 s / 0.61 s | 1.6 s / 0.58 s |

The memory came from four separate causes, each measured on its own run:

1. WPF UI's navigation kept every page ever shown in its page-to-item map, so a repeated round kept
   adding pages; the shell now keeps only the page on screen.
2. Hardware drawing put about 190 MiB of graphics-driver memory in the process. Software drawing is
   the default (owner's choice); **Settings → Display** turns the graphics card back on.
3. A page that has left holds native drawing memory until a full collection finalizes it, and the
   small managed heap (about 56–60 MiB) seldom asked for one. With causes 1 and 2 fixed, the working
   set still climbed about 3 MiB per page to 351 MiB (peak 365 MiB) before a collection dropped it to
   282 MiB. A non-blocking background collection, requested once the new page is idle, keeps it at
   230–259 MiB. Total GC pause over the run was 551 ms against 571 ms without it, and first-frame
   callbacks were unchanged.
4. The Sales History export turned each 500-bill page into one string, a large object, and grew the
   large-object heap by 159 MiB (export peak 462 MiB). It now reuses one builder and writes its
   chunks (383 MiB with cause 3 unfixed, 310 MiB with it).

On the store left at schema 36, the 1.1.0 journey met the update window and confirmed it. The
upgrade, including the verified pre-upgrade backup of the 1.8 GB store, took 20.3 s.
