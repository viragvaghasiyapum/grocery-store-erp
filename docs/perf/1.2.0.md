# Release 1.2.0 performance evidence — 5 November 2026

This is the same-machine pass for release 1.2.0 (release gates G-1, G-2 and G-5 in
[revised-plan-bugs.md](../../revised-plan-bugs.md)): release 1.1.0 (commit 05b8f26, schema 37) against
1.2.0 (schema 41). It is local evidence on the development PC, not the target-shop-PC acceptance that
§3 of the [revised plan](../../revised-implementation-plan.md) still requires.

- PC: VARK, i7-13700HX, 24 logical processors; ScaleAudit on .NET 10.0.8, SQLite 3.53.3. The OS file
  cache was never flushed.
- Store: the preserved schema-36 full-size fixture (47,010 products, 223,272 lots, 871,876 sales,
  5,193,017 sale lines; 1,807,351,808 bytes), first taken to schema 37 by the 1.1.0 build, as a shop
  on 1.1.0 has it. Every run started from a fresh copy of that schema-37 store; each 1.2.0 run first
  upgraded its copy to 41 with its own build. The 1.1.0 build came from a scratch worktree.
- Method: `ScaleAudit phase9-profile`, as for 1.1.0. Each operation runs once under the SQL trace, then
  10–30 times alone, then mixed: 300 cashier bills with voids and returns, four readers, purchase posts,
  damage, counts, vendor returns and one verified backup at once.
- Two passes. `run-ab.sh` ran three rounds (base, new; new, base; base, new) with each profile
  starting right after its copy and, for 1.2.0, its upgrade. `run-settled.sh` ran two more rounds
  (new, base; base, new) where every copy waited 120 s before the profile, then ran both full-history
  exports on the same copy.
- Evidence: `artifacts/data/revised-plan-bugs/g1-g2` (both scripts, every run's JSON and log,
  `compare.mjs` with `compare.txt` and `compare-settled.txt`, `stmt-diff.mjs`, `bench-reads.mjs` with
  `bench-reads.txt`). The store copies were deleted after the runs.

Every search stays far inside the 30 ms search gate at p95 (3.11 ms at most).

**Writes follow the store file, not the build.** In the first pass, 1.2.0's back-office writes
(purchase post and void, vendor return and cancel, damage, count review) were 1–4 ms slower than
1.1.0's. Each 1.2.0 copy had been profiled straight after its 10 s upgrade rewrote gigabytes of the
file. With both copies settled for 120 s, the same writes were 1.5–4 times faster on 1.2.0. The SQL
trace (`stmt-diff.mjs`) shows the same statements and triggers in both builds for those writes, and
fewer for sales after C-1: completing a bill runs 97 statements against 112, a void 137 against 164
and a partial return 147 against 166.

**Two small read differences.** The Products searches are 0.05–0.1 ms slower: they run T-1's query,
which prices each row from the lot a bill takes next (`ix_lot_fefo`). It visits a quarter of the rows
(the SKU search: 160 VM steps against 650) but compiles a longer statement with more correlated
subqueries. Opening a finalized year's P&L is 0.2–0.3 ms slower with identical SQL and identical C#
(no change to `AnnualCloseService`, `PeriodGuard` or the read path since 1.1.0). SQLite alone shows
no difference (`bench-reads.txt`): opening a connection and loading the schema takes 2.16–2.20 ms on
schema 41 against 2.31–2.56 ms on 37 (126 triggers against 138, 68 tables against 72), and the three
statements of the read are within noise. The remainder is in the process; at under a millisecond on a
report opened by a click it was accepted.

**Dashboard** is 3 ms faster: its snapshot query, rebuilt on `ExpiryAlert` by the Phase 8 fixes,
runs 1.10 million VM steps against 1.71 million in the trace.

## Upgrade, storage, backup and recovery (G-1)

- 36 → 37 with the 1.1.0 build: 18 ms. 37 → 41 with the 1.2.0 build: 10.0–10.1 s on three copies,
  file cached, process peak 69 MiB, plus the verified pre-upgrade backup the app takes first. The
  update window's estimate uses 22 s per GiB for migration 39, measured at 37 s on 1.8 GB from a cold
  disk in the tax rehearsal.
- On the last upgraded copy, after the 1.2.0 profile's writes, all eight store checks passed:
  report-day and dashboard projections, integrity (45 s), foreign keys, every lot against its source
  documents (40 s at 73 MiB), sale lines after lot expiry and interrupted writes.
- A process killed after its lot update but before commit left no sale rows, no foreign-key
  violations and no lot mismatches, and `quick_check` was ok.
- Verified backup of the store with no other load: 15.9 s at 71 MiB (542 MB zip). Restore into an
  empty data root: 18.6 s at 87 MiB; the restored store passed the eight checks, and the original
  passed them again.

**A panel kept its page (B-7).** Before the fix, three rounds with the panels peaked at 329 MiB, but
the working set at each round's end rose about 10 MiB a round. Ten rounds took it from 270 to 350 MiB
(process peak 375 MiB, 383 MiB after the export), and the managed heap left after full collections
from 36 to 106 MiB; without the panels it stayed flat. The pagers inside the Sales history bill panel
and the asset timeline subscribed to the session-long language source twice (loaded with the page while
the panel was collapsed, and again when it first opened) and unsubscribed once, so each visit kept its
page. With the fix the same ten rounds stay at 267–285 MiB.
